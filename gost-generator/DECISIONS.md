# DECISIONS.md — самостоятельные решения и их причины

Формат: решение — причина — рассмотренные альтернативы.

## D1. Drag&drop файлов вкладки «Проверка» — только диалог в v1
Tkinter без дополнительных библиотек не даёт надёжного drop для CustomTkinter-окон
(tkinterdnd2 — новая runtime-зависимость, запрещена ТЗ §2).
Альтернатива: tkinterdnd2 — отклонена (запрет зависимостей); own OLE DnD на Windows — отклонена
(ломает кроссплатформенность). Абстракция «источник файла» в `dialogs.py` оставлена как точка
подключения (ТЗ §13).

## D2. Фикстуры `.docx` генерируются программно, бинарники в git не хранятся
ТЗ §15 прямо это предписывает: `tests/fixtures/make_fixtures.py` собирает правильный/сломанный
документы на stdlib; тесты вызывают его при отсутствии файлов. Альтернатива — коммит бинарей:
раздувает репо и не переживает изменения нормализатора.

## D3. Один профиль метаданных = один JSON-файл, активный — в state.json
Альтернативы: реестр-индекс (усложнение, рассинхрон), БД (запрещена ТЗ). CRUD + импорт/экспорт
покрывают §7.2.

## D4. Ключ пресета = имя файла без `.json`, `builtin` — флаг внутри JSON
Проще, чем отдельный индекс: список = сканирование двух каталогов (встроенные + пользовательские),
пользовательский пресет с именем builtin отбрасывается с явной ошибкой (см. D5).

## D5. Правка встроенного пресета невозможна («Сохранить» → «Сохранить как…»)
Прямой запрет ТЗ (§AGENT правила). Реализовано исключением `CannotEditBuiltinError`,
UI перехватывает его и предлагает новый ключ.

## D6. Нумерация «вторая страница = 2» — одна секция + `titlePg` + PAGE-поле
Единственный способ, не ломающийся в Word/LibreOffice и не требующий второй секции
(ТЗ §11.1.1, CHATBOT_TEMPLATE §5). Альтернатива `pgNumType start="2"` во второй секции —
хрупкая: ошибка вложенности sectPr даёт «1».

## D7. Оценка страниц в инспекторе — эвристика, поле `page` может быть `null`
Реальную пагинацию знает только Word. Ёмкость полосы считается из kегля и интервала правил;
для `VOLUME_FILL` это `info`, а не `error` (ТЗ §9). Альтернатива — рендер через LibreOffice
headless: внешняя зависимость, вне скоупа v1.

## D8. Нормализатор сохраняет `<name>.orig.docx` один раз
Перезапись бэкапа при повторном `gost fix` уничтожила бы оригинал. Повторный fix идемпотентен
и бэкап не трогает.

## D9. `check_docx.py` остаётся автономным скриптом (compat), движок приложения — `docx_inspector`
Дублирование проверок сознательное: скрипт обязан работать из терминала без приложения
(ТЗ §11.2), а GUI/CLI используют один движок через ядро. Общий код между ними не вводится,
чтобы не тянуть `app.core` в `python -I` окружение скрипта.

## D10. `arg_template` без плейсхолдеров → универсальная форма `[input, output, params_json]`
Совместимость со старыми скриптами вида `mkdocx.py in.md out.docx '{...}'` (ТЗ §8.2) — иначе
пришлось бы требовать мету у каждого файла.

## D11. `rules_hook` неизвестного скрипта = `postprocess`
Прямо предписано ТЗ §8.1 как значение по умолчанию: safest path — сначала сгенерировать,
потом привести к правилам.

## D12. CLI-тексты AGENTS.md/schemas/examples встроены в `app/cli_init.py` fallback-копиями
В собранном `gost.exe` репозитория нет; `gost init --agents` обязан работать автономно.
При наличии файлов на диске (режим разработки) берутся они — единый источник истины.

## D13. Год по умолчанию берётся из `datetime.date.today().year` везде
ТЗ §7.2/§11.1.8. В `profiles/default.json` в репозитории проставлен текущий год на момент
создания; приложение при пустом значении подставляет системный год, а не читает файл.

## D14. Поддержка только A4
Методичка клиента и ГОСТ 7.32 регламентируют A4; другие форматы — фиктивная функциональность.
`units.page_size()` молча приводит неизвестный размер к A4 вместо ошибки (документировано).

## D15. `gost check` над битым `.docx` — статус «Ошибка чтения», exit 1, без падения
Пакетный режим не должен прерываться на одном файле (ТЗ §10.3 приёмка); ошибка попадает
в `data.items[].status` и `errors[]` конверта.

## D16. Лог-панель опрашивает queue через `after(80ms)`
Обратные вызовы из рабочего потока в Tk небезопасны; поллинг очереди — стандартный
потокобезопасный паттерн CustomTkinter/Tk (ТЗ §12 «UI никогда не freezes»).

## D17. `multiprocessing` в стеке только для `freeze_support()`
Требование ТЗ §3.2.6 на будущее (журнал запусков v2); реальных пулов в v1 нет.

## D18. `pedagogical`/`free` пресеты отключают ГОСТ-специфичные проверки через ключи правил
(ТЗ §9 «проверки отключаются по ключам», §53 предупреждение AGENTS): `require_reference_in_text=false`,
`max_source_age_years=0`, `toc.required=false`, `strict=false` — без if-по-имени-пресета в коде.

## D19. Штатные скрипты ищутся в `sys._MEIPASS/scripts`, затем в `scripts/` проекта
`DataDirs.bundled_scripts()`: в собранном exe каталог данных пользователя пуст до первого
`gost init`, и без этого источника список генераторов был бы пуст (ТЗ §3.2.5 «первый старт
распаковывает скрипты и пресеты»). Альтернатива — копировать скрипты в home при старте: отклонена,
пользовательские правки перестали бы обновляться вместе с приложением.

## D20. Подсказки («откуда требование») — свой слой `widgets.with_tip`, не библиотека
`tooltip`-пакеты — новая runtime-зависимость (запрет ТЗ §2); Tk-`Balloon` недоступен в CustomTkinter
и не переживает смену темы. `with_tip` возвращает виджет, чтобы не разрывать цепочку конструктора.

## D21. Состояние приложения называется `app_state`, а не `state`
`ctk.CTk` уже владеет атрибутом `state` (Tk: normal/iconic/zoomed) — перезапись ломала бы
сворачивание окна. В `state.json` на диске ключи остались короткими (совместимость миграции).

## D22. Фикстура «сломанный документ» несёт 6 дефектов, внесённых мини-редактором OOXML
`make_broken` правит Arial/поля/интервал/номер страницы/отступ строками-заменами и отдельно
центрирует подпись таблицы (ТЗ §15 требует, чтобы находились все внесённые дефекты). Хранить
битый `.docx` в git не стали — см. D2. Альтернатива «собрать документ заведомо неправильным
стилем» отклонена: инспектор проверяет фактические свойства, и часть дефектов не воспроизвёлась бы.

## D23. Статусы в отчётах — русские (`STATUS_LABELS`), машинные ключи остаются английскими
Конверт §19.4 отдаёт `ok|violations|warnings|read_error|...`, человек видит «Есть ошибки»,
«Ошибка чтения». Разделение нужно, чтобы агенты парсили стабильные ключи, а UI-читатель —
понятный текст (ТЗ §10.3). Альтернатива — русские ключи в JSON: сломала бы контракты схемы.

## D24. OK-статус = `Без замечаний`, а не «OK»
Таблица сводки читается глазами в диалоге сдачи работы; «OK» не отличался бы от кодаseverity.

## D25. Окно вписывается в экран, сохранённая позиция клампится
`_screen_default_w/h` берут габариты монитора минус запас на рамку/панель задач,
`_geometry_string` ограничивает `x`/`y` (`POSITION_MARGIN`). Без этого на 1366×768 нижний край
(вместе с панелью журнала и кнопкой «Сгенерировать») уезжал за экран после перезапуска.

## D26. `safe()` пробрасывает аргументы колбэка, диалог ставится в UI-очередь
Первая реализация обёртки принимала только `fn` без аргументов, а `generator_run` запускал
`Thread(target=safe(self._worker), args=(info, kwargs))` → `TypeError` внутри потока, и генерация
в GUI не завершалась никогда. Диалог исключения — Tk-виджет: из рабочего потока его показывают
через `app.post`, иначе нарушается правило «Tk только в главном потоке» (ТЗ §12).

## D27. Автоимя выходного файла строится по теме из формы, а не по профилю
Порядок совпадает с `job._default_output` (ТЗ §19.7): тема параметра → тема meta → имя → файл
скрипта. Пока поле вывода не тронуто вручную, `_sync_output_name` пересобирает имя при правке
темы; вписанный путь остаётся как есть. Иначе все отчёты одного дня назывались бы фамилией автора.

## D28. Первый параметр `strings.t()` — `text_key`, не `key`
Плейсхолдеры строк форматирования включают `{key}` (`rules_saved`, `prof_created`), и вызов
`t("rules_saved", key=...)` падал с «multiple values for argument 'key'» на реальном сохранении
пресета. Ключ словаря переименован, плейсхолдеры остались.

## D29. Падение скрипта показывается диалогом с хвостом вывода
ТЗ §15.5: красный бейдж при свёрнутой панели журнала замечен не был бы; `generator_run`
дописывает последние строки stderr/stdout в `dialogs.show_info` и возвращает кнопку в `normal`.

## D30. Нормализация приводит документ к активному пресету, включая ориентацию
Педагогический пресет альбомный, ГОСТ — книжный, поэтому «Применить правила» после генерации
`make_games` разворачивает страницы в книжную. Это ожидаемое поведение (флаг «Применить правила
после генерации» означает именно применение выбранного пресета), а не ошибка нормализатора;
для педагогических документов нужно выбирать `pedagogical` (см. предупреждение AGENTS.md).

## D31. В job-конверте пустой `input` отсутствует, а не равен `null`
Схема §19.7 не допускает `null` в `input`, а универсальная форма оставила бы поле пустым у
скриптов без входного файла. `generator_tab._job_dict` просто не добавляет ключ.

## D32. UI-смоук-тесты пропускаются без `DISPLAY`
Тесты реального окна (`tests/test_ui_smoke.py`) создают `ctk.CTk`; на headless-машине (CI-артефакт,
сборка exe) это не баг, а отсутствие окружения — `unittest.skipUnless`. Те же ветки логики
покрываются CLI-тестами, поэтому покрытие не падает.

## D33. `gost init --agents` внутри репозитория не копирует файл в себя
`_copy_or_write` даёт `SameFileError`, когда `base` — корень репозитория: источник и приёмник
совпадают. Теперь совпадение (`resolve()`-пути) и отсутствующий источник обрабатываются как
«писать нечего», а `AGENTS.md` тоже читается с диска (единый источник истины D12), и встроенная
копия остаётся только для собранного exe.

## D34. CI-smoke проверяет CLI на реально генерируемой фикстуре
Шаг сборки обращался к `tests/fixtures/sample_good.docx`, которого `make_fixtures.py` не создаёт,
и smoke падал бы на чистом Windows-раннере. Правка: `fixtures_good.docx` + `--fail-on error`
(документ даёт только `info`-рекомендации, поэтому exit 0 ожидаем).

## D35. Linux-пакеты (AppImage/deb) в v1 не собираются
Makefile ссылался на `packaging/appimage/build.sh` и `packaging/deb`, которых в репозитории нет, —
это запрещённые ТЗ §0 заглушки, цели удалены. ТЗ (§14) требует Windows-артефакт и portable-режим;
на Linux продукт запускается из исходников (`python -m app`), а `gost init --dir` покрывает
раскладку «рядом с приложением». Альтернатива — написать фиктивные spec-файлы: отклонена.

## D36. Пункт §15.12 (Windows exe без установленного Python) проверяется только в CI
PyInstaller не собирает Windows exe на Linux (Wine/Xvfb на машине приёмки нет, установка — вне
полномочий). Ответственность перенесена в workflow `build-windows.yml`: сборка обоих exe,
`gost doctor`/`gost check` smoke и zip с `portable.flag`. В `CHANGELOG.md` пункт помечен
«не проверялся локально», а не «пройден».

## D37. Патч совместимости CustomTkinter живёт в `app/ui/__init__.py`, а не в `main.py`
На CPython 3.14 `event.widget` у колеса мыши бывает строкой-путём Tk (виджеты нативного
`filedialog` не имеют python-обёртки), и штатный `CTkScrollableFrame._check_if_valid_scroll`
падает с `AttributeError: 'str' object has no attribute 'master'` — приложение закрывается прямо
в диалоге «Добавить скрипт…». Обходной код кладём в инициализацию пакета `app.ui`, потому что
`bind_all` срабатывает глобально и патч должен быть наложен до сборки первого окна; CLI-пути
(`app.cli`) пакет не импортируют, а при отсутствии GUI-зависимостей патч молча пропускается.
Альтернативы — патчить `site-packages` (нельзя в собранном exe) и перепривязать обработчик
(задвоило бы прокрутку) — отклонены. Регрессия: `tests/test_ui_smoke.py` + негативный контроль
живым диалогом (без патча 160 ошибок, с патчем 0).

## D38. «Добавить скрипт…» копирует файл в каталог скриптов, а не добавляет по внешнему пути
Раньше подтверждение показывалось текстом-утверждением («Скрипт скопирован…») и копирование не
обрабатывало `OSError`, то есть отказ выглядел как успешное добавление. Теперь диалог задаёт
вопрос (`gen_add_copy`) и предлагает «Отмена» = добавить по исходному пути, сбой копирования
попадает в журнал (`gen_add_copy_error`). Копирование выбрано потому, что ТЗ §12 требует, чтобы
скрипты пользователя хранились в каталоге скриптов и переживали перезапуск (внешний путь мог
исчезнуть), а `warn_external_script` остаётся обязательным шагам перед любым исполнением.

## D39. Высоту журнала задаём текстовому полю, а не панели
`LogPanel(height=…)` конфигурировал фрейм, но `CTkTextbox` без явного `height` просит 200 px,
и propagate раздувал панель до ~240 px. На экране 1366×768 из-за этого сайдбар получал 404 px
при потребности 516 px, и нижние кнопки («О программе», «Тема») не рисовались вовсе — первая
попытка лечения (две кнопки в ряд) лишь прятала симптом и обрезала подпись. Теперь
`height` панели пересчитывается в `height` текстового поля (`PANEL_CHROME` — полоса заголовка),
кнопки снова в один столбец, а UI-тест `test_sidebar_bottom_buttons_are_not_clipped` фиксирует
и видимость, и отсутствие обрезки.

## D40. Пустой бейдж результата не пакуется
Бейдж со строкой `""` Tk рисует как цветную заглушку, и в ряду кнопок генерации до первого
запуска выглядел «мёртвой» кнопкой. `set_result_badge()` пакует/снимает бейдж по непустоте
текста — тот же приём уже применялся к «грязным» бейджам правил и профиля (D-ряд §15.1).
